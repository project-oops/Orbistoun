# 627. Nine decisions were written and never indexed, and the generator was one directory up

**2026-09-16** - `bin/orbistoun`, `docs/DECISIONS.md`, `CLAUDE.md`, closing `REQ-20260915T0929Z-2113`

`REQ-20260915T0929Z-2113` asked for a decision on how the worker's output reaches the window. D695
answered it on 2026-09-15 and the request's own note said what was left: *"`docs/DECISIONS.md` does
not list D695 yet - the index needs regenerating."* It was not one entry missing. **Nine were:**
D691, and D693 through D700 - every decision taken across two days.

## Why nothing noticed

`./bin/orbistoun decisions` reads the index and asks whether its numbers are sound: duplicated,
reserved-and-never-spent, listed-in-the-backlog-but-no-longer-duplicating. Three checks, all
pointed at the index. **None of them asks whether the index describes the files.** A decision
written and never listed is invisible in the one place `CLAUDE.md` tells every session to consult,
and no gate is looking.

The worklog gate one directory across has had exactly this check all along - `not listed in
docs/WORKLOG.md` - so the shape was already agreed. That check now exists for decisions too, as a
`warn` for the same reason it is a warn there: an entry written minutes ago is not a broken tree.
Watched reporting, with a temporary `D998` file that was then deleted.

## The detour, which is the part worth recording

`CLAUDE.md` says the table is generated by `tools/split-decisions.sh`. From inside this repository
that path reads as *this* repository's `tools/`, which holds shader fixtures, a toolchain and the
differential reference - and no such script. So I concluded the generator had been deleted, and
started hand-writing the nine rows.

It exists. It lives in the **collection's** `tools/`, one directory up, and `docs/README.md` has
always shown it correctly as `tools/split-decisions.sh --index orbistoun` run from there. A relative
path in a per-repository instruction file that resolves against a different root is the whole bug,
and it is the kind that costs every session the same twenty minutes.

Having found it, the hand-written rows went in the bin and the generator produced the index. Worth
noting that it agreed with them: same nine entries, same files, same statuses - the only difference
was that the generator capitalises the title as the file heading writes it, and I had lower-cased to
match the rows above. That is a good outcome for a bypass caught in time, and not a reason to trust
the next one. `CLAUDE.md` now names the collection root explicitly, shows both commands, and says
the thing that was nowhere: **writing a decision file does not index it** - `decide` reserves the
number and creates the file, and nothing adds the row.

## What is now true

- 710 decision files, 710 index rows, nothing unindexed.
- The gate reports an unlisted entry instead of ignoring it.
- `2113`'s acceptance is met: D695 is written, indexed, and linked from the request.

## Files

- `docs/DECISIONS.md` - regenerated by the collection's generator, not by hand.
- `CLAUDE.md` - the generator's real location, both commands, and that `decide` does not index.
